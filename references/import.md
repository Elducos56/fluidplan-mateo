# From a source to a plan

## By format

| Source | Read with | Notes |
|---|---|---|
| `.md`, `.txt` | the Read tool | directly |
| `.pdf` | the Read tool, in chunks: `pages: "1-20"`, then `"21-40"`… | page images are visible; transcribe tables by hand |
| `.docx` | `node <skill>/engine/fluidplan.mjs import <file.docx> --out docs/fluidplan/<id>/source` | writes `source.md` and `media/`; then read `source.md` |
| `.docx` (fallback) | the command falls back to `pandoc` if it is installed | if both fail: ask for a .md or .pdf export |
| a request in the conversation | the conversation + exploring the code | see `authoring.md` § 8 |

The built-in .docx reader (no dependencies) renders: headings (`Heading` / `Title` styles, English
or French names), paragraphs, bold and italic, links, bulleted and numbered lists (nested), tables
(merged cells approximated), images, text boxes. It skips headers, footers, comments, text deleted
in tracked changes, and the table of contents. Known limits: footnotes are not imported, heading
numbers generated by Word are lost, charts and SmartArt are skipped (a warning says so). Reread the
source when in doubt.

## Storing the source

- Leave the original document where it is; record its path in `source.path` (relative to the
  project root) and its format in `source.kind`.
- Useful images (screenshots, diagrams, project icons) are copied **and downscaled** into
  `docs/fluidplan/<id>/assets/`; reference them as `assets/<name>`.
- `source_ref` on every decision: the section or page it comes from.

## From text to decisions

1. Read the whole document before writing a single decision.
2. List the themes (→ pages), the open questions (→ `choice`), the lists (→ `items`), the
   adjustable figures (→ `number`), the order of the work (→ `phases` + `order`).
3. For each decision: take the document's proposal, write `why` (often implicit in the document:
   make it explicit), fill in the pros / cons of the options.
4. Write the tasks: what the document says about the implementation, completed by exploring the
   code if there is any.
5. `check`, `snap`, reread — then launch.

A proposal document that is already partly settled: what is agreed becomes `minor` decisions
(accepted in one click) or directly tasks of a neighboring decision.
